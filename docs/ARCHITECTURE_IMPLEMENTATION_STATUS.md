# VIXEN five-layer implementation status

The requested TOP / EXECUTIVE OS, MIDDLE OS, BACK OS, VIXEN KERNEL, and FRONT OS model is the internal architecture for this VIXEN project. It is not visitor-facing navigation.

## Current code foundation

- **TOP / EXECUTIVE OS** — `lib/executive/platform-readiness.ts` records evidence gates and evaluates whether a capability has the proof needed for release. Admin, moderation, finance, and audit dashboards remain to be built.
- **MIDDLE OS** — `lib/application/` contains pricing, an audited creator-content access workflow, and a tested private-video join workflow. The join workflow verifies identity and booking, applies the Kernel policy, requires durable audit, and then requests a short-lived participant credential. No video provider is connected.
- **BACK OS** — `lib/adapters/service-contracts.ts` defines server-side service boundaries. Supabase Auth is connected for VIXEN email/password signup, sign-in, callback/session exchange, protected account access, and password recovery. The password-recovery flow is covered by CI and its public unauthenticated route redirects safely; actual reset-email delivery and a full token-to-password-change cycle still need live end-to-end verification. Proton addresses are accepted as email addresses, not as Proton OAuth. Application data persistence and adapters for payments, commerce, creator storage, n8n, LLMs, and video are not established as active. Payment confirmation and video room credentials must come from trusted server integrations.
- **VIXEN KERNEL** — `lib/kernel/` owns illustrative membership prices, tested NINE subscription-preview cent rounding, verified role types, creator content access decisions, a tested private-video join policy, and audit-event contracts. The private-video policy fails closed unless an active adult-verified member or the booked creator joins the matching creator-accepted, paid booking inside its scheduled window. Ledger, rewards, journey, and further domain rules remain to be built and tested before activation.
- **FRONT OS** — the existing Next.js App Router under `app/` renders VIXEN pages. The public homepage links to `/about`, which shows the supplied Nine Tail Fox mascot and its parent-company relationship. `/sign-up` provides separate member and creator account paths; Supabase email/password signup, sign-in, and password recovery are implemented. A production HTML fetch on 2026-10-07 returned HTTP 200 for `/sign-up`; the unauthenticated `/account/reset-password` route correctly returned the signup page after its protected redirect. This verifies route behavior, not a completed reset-email round trip. `/member-preview` links to visual message and private-video session previews, filters its sample creator feed by name, handle, category, title, or description, and routes sample Follow actions to member sign-up. The filter and links do not create persisted follows, messages, bookings, or payments; message preview screens route search to creator discovery. The PR #39 composer is a local draft walkthrough only; text stays in page memory and is neither transmitted nor persisted. The private-video session preview now has an interactive two-step listing and checkout walkthrough with illustrative durations/prices, transparent availability and cancellation disclosures, creator-controlled boundaries, and browser permission timing; the sample flow never reserves or charges. Paid membership tiers link to a review-only checkout preview that carries the selected sample creator, displays tier inclusions/exclusions and planned 33⅓% NINE math with integer cent rounding, and never charges or creates a subscription. `/creator/studio` is a responsive visual preview of profile, content/drop, memberships, messaging, sessions, and earnings areas; none of those creator tools save, publish, or process money. `/events` previews planned VIP/VVIP private events with 21+ eligibility, required active membership card, creator opt-in, and explicit consent boundaries; reservations are disabled and no event is scheduled. The Vercel production deployment for main commit `69e5b45c018ba3b472b66d93c49bd109b3a927af` is READY. The CI run for PR #48 passed lint, spelling, kernel policy tests, TypeScript checking, and production build. A production HTML fetch returned HTTP 200 for `/sign-up`; `/account/reset-password` redirects unauthenticated visitors to signup. All creator profiles, conversations, and session cards remain sample UI; messaging, checkout, bookings, and video rooms are not live. Device camera/microphone access must happen only after the participant chooses to join and the browser grants permission.

The join workflow does not access camera or microphone devices. Only the browser can request device permission, after the member explicitly continues from a successfully authorized session screen. Provider credentials are participant-bound, short-lived (at most three minutes), and must never be logged or exposed before authorization.

## Dependency rules

1. Front OS pages call Middle OS use cases; they do not own business prices or entitlement rules.
2. Middle OS workflows call Kernel rules and Back OS interfaces.
3. Back OS implementations must not make independent authorization, price, or entitlement decisions.
4. TOP / Executive OS gates production capabilities and sensitive operations; hiding a control in the UI is not authorization.
5. No capability is marked active without its required operational and end-to-end evidence. `privateVideoSessions` remains planned until payment, signaling, consent, moderation, and cross-device verification are live.
6. The browser requests camera and microphone only after an eligible participant explicitly enters a paid session; denying either permission must not silently bypass the prompt or expose private media.
